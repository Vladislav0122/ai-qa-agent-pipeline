# SKILL: task_design (Проектирование задач Jira)

## 1. Роль и Назначение
Навык трансформирует согласованные требования и артефакт ревью (`STEP1_REQUIREMENT_REVIEW.md`) в четко структурированные, готовые к разработке и оценке сущности Jira (Epic, User Story, Task, Sub-Task).

---

## 2. Принципы проектирования задач (Design Rules)

### 2.1. Критерии INVEST для User Stories
- **I (Independent)**: Задачи должны быть максимально независимы друг от друга для гибкого планирования.
- **N (Negotiable)**: Оставляют пространство для инженерного решения реализации.
- **V (Valuable)**: Несут понятную ценность конечному пользователю или бизнесу.
- **E (Estimable)**: Требования прозрачны для командной оценки.
- **S (Small)**: Размер задачи укладывается в один спринт (1–3 дня разработки).
- **T (Testable)**: Имеются измеримые критерии приемки (Acceptance Criteria).

### 2.2. Стандарты описания
1. **Канонический формат User Story**:
   > **Как** [роль / тип пользователя],  
   > **Я хочу** [действие / возможность системы],  
   > **Чтобы** [получаемая бизнес-ценность / результат].

2. **Acceptance Criteria (Критерии приемки) в формате Given-When-Then**:
   - Описывают ожидаемое поведение системы для утвержденного функционала.
   - Обязательно покрывают как позитивный сценарий, так и валидационные ошибки.

3. **Definition of Done (DoD)**:
   - Чек-лист готовности фичи к релизу (Unit-тесты, Code Review, Swagger/OpenAPI документация, QA-проверка).

### 2.3. Защита скоупа от неподтвержденных бизнес-правил (Scope Integrity)
> ⛔ **СТРОГОЕ ПРАВИЛО**: Запрещено самовольно включать в задачи спринта неподтвержденные бизнес-правила или технические решения (например: конкретные алгоритмы блокировки, жесткую привязку к Redis, не согласованные лимиты).  
> Все технические идеи и предложения оформляются **исключительно** в отдельный блок: `3. Рекомендации и архитектурные исследования (Spikes / Suggestions)` и требуют согласования PO и Техлида перед взятием в работу.

---

## 3. Методология декомпозиции

- **Epic**: Верхнеуровневая фича (например: *"Модуль управления паролями в личном кабинете"*).
- **User Story**: Пользовательский функционал с прямой бизнес-ценностью.
- **Technical Task**: Инженерные задачи строго по утвержденным спецификациям (например: *"Реализация API эндпоинта смены пароля"*).
- **Spike / Exploration Task**: Задачи на исследование и прототипирование не до конца определенных требований (например: *"Spike: Выбор оптимального механизма Rate Limiting и инвалидации сессий"*).

---

## 4. Критерии Quality Gate 2 (Task Quality Gate)

Перед сохранением артефакта проверяется:
- [x] Задачи спроектированы **строго на базе согласованных требований** и решений из `STEP1_REQUIREMENT_REVIEW.md`.
- [x] Ни одна User Story не содержит размытых условий приемки.
- [x] Неподтвержденные требования отделены от основного скоупа и вынесены в Spikes/Recommendations.
- [x] Присутствуют Acceptance Criteria на позитивные и негативные ветвления.
- [x] Указаны взаимосвязи задач (`Blocks`, `Relates to`, `Depends on`).

```markdown
- **Epic Key / Name**: [PROJ-EPIC-01: Название эпика]
- **Бизнес-цель**: Краткое описание решаемой задачи
- **Статус Quality Gate 2**: [✅ PASSED | ❌ FAILED]

---

## 2. Утвержденные задачи спринта (Sprint Backlog Items)

### [PROJ-101] User Story: [Краткое название]
- **Тип задачи**: User Story
- **Приоритет**: Highest / High / Medium / Low
- **Компоненты**: [Frontend / Backend / Auth / etc.]
- **Описание**:
  > **Как** ...  
  > **Я хочу** ...  
  > **Чтобы** ...

#### Acceptance Criteria (AC):
- **AC-1 (Happy Path)**:
  - **Given**: ...
  - **When**: ...
  - **Then**: ...
- **AC-2 (Validation / Error Flow)**:
  - **Given**: ...
  - **When**: ...
  - **Then**: ...

---

## 3. Рекомендации и архитектурные исследования (Proposed Spikes & Suggestions)
> *Данный блок содержит технические инициативы и предложения по неполным требованиям. Они не входят в основной скоуп спринта до утверждения PO.*
- **[PROJ-SPIKE-01] Spike**: Исследование параметров защиты от перебора паролей (Rate Limiting).
- **[ARCH-NOTE-01] Предложение**: Анализ механизма инвалидации сессий при распределенной архитектуре.
```

---

## 6. Критерии завершения (Completion Criteria)

Работа скилла `task_design` считается успешно завершенной, если:
1. **Трассируемость 100%**: Каждое утвержденное требование из шага 1 отражено в User Story или Task.
2. **Чистота скоупа**: Никакие неподтвержденные бизнес-правила не добавлены в утвержденные AC.
3. **Формат критериев приемки**: Все AC сформулированы в проверяемом формате Given-When-Then.
4. **Успешный Quality Gate 2**: Все пункты чеклиста Quality Gate 2 отмечены как выполненные.
5. **Сохранен артефакт**: Файл `STEP2_JIRA_TASKS.md` сохранен и готов для передачи в `test_design`.
