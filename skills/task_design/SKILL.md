# SKILL: task_design (Проектирование задач Jira)

## 1. Роль и Назначение
Навык трансформирует абстрактные требования и артефакт ревью (`STEP1_REQUIREMENT_REVIEW.md`) в четко структурированные, готовые к разработке и оценке сущности Jira (Epic, User Story, Task, Sub-Task).

---

## 2. Принципы проектирования задач (Design Rules)

### 2.1. Критерии INVEST для User Stories
- **I (Independent)**: Задачи должны быть максимально независимы друг от друга для гибкого планирования в спринты.
- **N (Negotiable)**: Оставляют пространство для инженерного решения реализации.
- **V (Valuable)**: Несут понятную ценность конечному пользователю или бизнесу.
- **E (Estimable)**: Требования достаточно прозрачны для оценки командой (Story Points / часы).
- **S (Small)**: Размер задачи укладывается в один спринт (оптимально 1-3 дня разработки).
- **T (Testable)**: Имеются измеримые критерии приемки, позволяющие QA однозначно подтвердить готовность.

### 2.2. Стандарты описания
1. **Канонический формат User Story**:
   > **Как** [роль / тип пользователя],  
   > **Я хочу** [действие / возможность системы],  
   > **Чтобы** [получаемая бизнес-ценность / результат].

2. **Acceptance Criteria (Критерии приемки) в формате Gherkin (Given-When-Then)**:
   - Должны покрывать как позитивный сценарий (Happy Path), так и валидационные/ошибочные ветки.
   - Пример:
     ```gherkin
     Сценарий: Успешная смена пароля
       Дано: Пользователь авторизован в системе
       Когда: Пользователь вводит валидный текущий пароль и новый пароль, соответствующий политике безопасности
       И: Нажимает кнопку "Сохранить"
       Тогда: Система обновляет пароль в БД
       И: Отображает сообщение "Пароль успешно изменен"
     ```

3. **Definition of Done (DoD)**:
   - Чек-лист готовности фичи (Unit-тесты написаны, Code Review пройден, API задокументировано в Swagger, QA-проверка пройдена, логирование настроено).

---

## 3. Методология декомпозиции

- **Epic**: Верхнеуровневая фича (например: *"Модуль аутентификации и восстановления доступа"*).
- **User Story**: Пользовательский функционал (например: *"Смена пароля в личном кабинете"*).
- **Technical Task**: Инженерные доработки, не видимые пользователю напрямую (например: *"Хеширование паролей алгоритмом Argon2id в UserService"* или *"Настройка Rate Limiting на эндпоинт POST /api/v1/auth/password/change"*).
- **QA Sub-task**: Задачи на тест-дизайн, подготовку тестовых данных и регрессионное тестирование.

---

## 4. Критерии Quality Gate 2 (Task Quality Gate)

Перед сохранением артефакта проверяется:
- [x] Все ключевые сценарии из требований Confluence отражены в задачах.
- [x] Ни одна User Story не содержит размытых условий приемки.
- [x] Присутствуют Acceptance Criteria на негативные ветвления (ошибки валидации, неверные пароли, лимиты запросов).
- [x] Указаны взаимосвязи задач (`Blocks`, `Relates to`, `Depends on`).

---

Артефакт должен строго следовать следующей структуре:

```markdown

- **Epic Key / Name**: [PROJ-EPIC-01: Название эпика]
- **Бизнес-цель**: Краткое описание решаемой задачи
- **Архитектурный контекст**: Задействованные сервисы, компоненты

---

## 2. Декомпозиция пользовательских историй (User Stories)

### [PROJ-101] User Story: [Краткое название]
- **Тип задачи**: User Story
- **Приоритет**: Highest / High / Medium / Low
- **Компоненты**: [Frontend / Backend / Auth / etc.]
- **Описание**:
  > **Как** ...  
  > **Я хочу** ...  
  > **Чтобы** ...

#### Acceptance Criteria (AC):
- **AC-1 (Happy Path)**:
  - **Given**: ...
  - **When**: ...
  - **Then**: ...
- **AC-2 (Validation Error)**:
  - **Given**: ...
  - **When**: ...
  - **Then**: ...
- **AC-3 (Security / Limits)**:
  - **Given**: ...
  - **When**: ...
  - **Then**: ...

#### Definition of Done (DoD):
- [ ] Логика реализована в соответствии с AC
- [ ] Unit-тесты покрывают ветвления (code coverage >= 80%)
- [ ] Swagger-спецификация обновлена
- [ ] Пройден ревью безопасности
- [ ] Тест-кейсы разработаны и пройдены в TMS
```
