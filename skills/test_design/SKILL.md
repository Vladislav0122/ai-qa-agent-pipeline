# SKILL: test_design (Проектирование тест-кейсов)

## 1. Роль и Назначение
Навык отвечает за формирование тестовой модели на основе согласованных задач Jira (`STEP2_JIRA_TASKS.md`) и требований Confluence с учетом замечаний ревью (`STEP1_REQUIREMENT_REVIEW.md`). Результат адаптирован для экспорта/импорта в современные TMS (Test IT, Allure TestOps, TestRail).

---

## 2. Применяемые техники тест-дизайна (Test Design Techniques)

Тип и количество проверок определяются природой самого требования и применяемой техникой:

### 2.1. Классы эквивалентности (Equivalence Partitioning — EP)
- Выделение классов валидных и невалидных входных данных.
- Один тест-кейс на каждый выделенный класс эквивалентности для исключения избыточности.

### 2.2. Анализ граничных значений (Boundary Value Analysis — BVA)
- Применяется для числовых параметров и строк фиксированной длины (например, длина пароля от $N_{min}$ до $N_{max}$):
  - Значения на границах: $N_{min}$, $N_{max}$.
  - Предграничные и заграничные значения: $N_{min}-1$, $N_{min}+1$, $N_{max}-1$, $N_{max}+1$.

### 2.3. Таблицы решений (Decision Tables)
- Применяются для комбинированных бизнес-правил (сочетание полей «старый пароль», «новый пароль», «подтверждение»).

### 2.4. Тестирование состояний и переходов (State Transition)
- Применяется при проверке изменения статусов сессий и учетных записей.

### 2.5. Предугадывание ошибок и исследовательские проверки (Error Guessing)
- Проверка спецсимволов, пробелов, XSS/SQL инъекций, двойных кликов и сетевых сбоев.

> 💡 **Принцип обоснованного покрытия**: Отсутствует искусственное требование «ровно 1 позитивный и 1–2 негативных на каждый AC». Количество и тип проверок определяются сущностью требования: для чисто информационных элементов достаточно одной позитивной проверки; для критических полей ввода формируется исчерпывающий набор граничных и негативных тестов.

## 3. Структура тест-кейса для TMS

Каждый тест-кейс должен содержать стандартизированный набор атрибутов:
- **ID / Key**: Уникальный идентификатор (например: `TC-SEC-001`).
- **Title (Название)**: Действие и ожидаемый результат в повелительном наклонении.
- **Priority**: Critical / High / Medium / Low.
- **Type**: Positive / Negative / Boundary / Security.
- **Layer**: UI / API / Integration.
- **Traceability Link**: Ссылка на задачу Jira и конкретный AC (например: `SEC-101 -> AC-1`).
- **Preconditions (Предусловия)**: Начальное состояние системы и тестовые данные.
- **Steps & Expected Results**: Пошаговый сценарий действий с однозначным результатом для каждого шага.
- **Postconditions (Постусловия)**: Очистка или сброс тестового состояния.

## 4. Критерии Quality Gate 3 (Test Quality Gate)

Перед сохранением артефакта проверяется:
- [x] **Полнота покрытия**: 100% утвержденных Acceptance Criteria покрыты тестами соответствующего типа.
- [x] **Обоснованность техник**: Для валидации полей применен анализ граничных значений (BVA) и эквивалентное разбиение (EP).
- [x] **Чистота от домыслов**: Тест-кейсы проверяют только утвержденные требования; неподтвержденные гипотезы (например, лимиты брутфорса без согласования) не тестируются как базовая функциональность.
- [x] **Атомарность и воспроизводимость**: Каждый тест-кейс проверяет конкретное поведение, шаги содержат явные тестовые данные.

## 6. Критерии завершения (Completion Criteria)

Работа скилла `test_design` считается успешно завершенной, если:
1. **100% трассируемость**: Каждый Acceptance Criterion из `STEP2_JIRA_TASKS.md` связан минимум с одним тест-кейсом.
2. **Обоснованное применение техник**: Приведены BVA, EP или Decision Tables там, где это необходимо.
3. **Готовность к импорту в TMS**: Все атрибуты (ID, Layer, Preconditions, Steps, Expected Results) заполнены без заглушек типа `TBD`.
4. **Успешный Quality Gate 3**: Все проверки чеклиста Gate 3 выполнены.
5. **Сохранен артефакт**: Файл `STEP3_TEST_DESIGN.md` сохранен и готов для включения в финальный отчет.
