## 2. Детальные тест-кейсы для импорта в TMS

### [TC-SEC-001] Успешная смена пароля валидными данными (Happy Path)
- **Приоритет**: Critical
- **Тип**: Positive
- **Слой**: UI
- **Трассировка**: `SEC-101 -> AC-1`, `SEC-102`
- **Предусловия**:
  1. Пользователь зарегистрирован с логином `qa_user_01@test.com` и паролем `CurrentPass123!`.
  2. Пользователь авторизован в Web-интерфейсе и находится на странице `/settings/security`.
- **Тестовые данные**:
  - Поле "Текущий пароль": `CurrentPass123!`
  - Поле "Новый пароль": `NewSecretPass456#`
  - Поле "Подтверждение": `NewSecretPass456#`

| № | Действие (Step) | Ожидаемый результат (Expected Result) |
|---|---|---|
| 1 | Ввести `CurrentPass123!` в поле "Текущий пароль" | Значение скрыто маской (`••••••••`), иконка "показать пароль" доступна. |
| 2 | Ввести `NewSecretPass456#` в поле "Новый пароль" | Все 3 индикатора сложности горят зеленым цветом (длина, цифры, спецсимволы). |
| 3 | Ввести `NewSecretPass456#` в поле "Подтверждение" | Ошибок несовпадения нет. Кнопка "Сохранить изменения" активна. |
| 4 | Нажать кнопку "Сохранить изменения" | 1. Отображается всплывающее сообщение зеленого цвета: "Пароль успешно обновлен".<br>2. Все поля формы сброшены в пустое состояние.<br>3. Сессия пользователя в текущей вкладке сохраняется. |
| 5 | Открыть режим "Инкогнито", перейти на страницу логина и авторизоваться с новыми учетными данными | Авторизация успешна. Старый пароль `CurrentPass123!` более не принимается системой. |

### [TC-SEC-002] Граничный анализ длины пароля: нижняя граница (BVA: 7, 8 символов)
- **Приоритет**: High
- **Тип**: Boundary Value Analysis
- **Слой**: UI & API
- **Трассировка**: `SEC-101 -> AC-2`
- **Предусловия**: Пользователь находится на форме смены пароля.

| № | Действие (Step) | Ожидаемый результат (Expected Result) |
|---|---|---|
| 1 | Заполнить "Текущий пароль" валидным значением | Поле заполнено. |
| 2 | Ввести в "Новый пароль" 7 символов (`Pass1!a` - `min-1`) | Под полем отображается валидационная ошибка: *"Минимальная длина пароля 8 символов"*. Кнопка "Сохранить" заблокирована. |
| 3 | Дописать 1 символ до 8 символов (`Pass1!ab` - `min`) | Сообщение об ошибке длины исчезает, чекбокс "Минимум 8 символов" становится зеленым. |
| 4 | Отправить API запрос `PUT /api/v1/auth/password/change` с телом `{"newPassword": "Pass1!a"}` (7 символов) | Ответ `400 Bad Request`, тело ошибки: `{"code": "PASSWORD_TOO_SHORT", "message": "Min length is 8"}`. |

### [TC-SEC-003] Граничный анализ длины пароля: верхняя граница (BVA: 32, 33 символа)
- **Приоритет**: High
- **Тип**: Boundary Value Analysis
- **Слой**: UI & API
- **Трассировка**: `SEC-101 -> AC-2`
- **Предусловия**: Пользователь находится на форме смены пароля.

| № | Действие (Step) | Ожидаемый результат (Expected Result) |
|---|---|---|
| 1 | Ввести в "Новый пароль" ровно 32 валидных символа (`A1!bcdefghij1234567890abcdefghij`) | Пароль принимается, индикаторы сложности активны. |
| 2 | Добавить 33-й символ (`A1!bcdefghij1234567890abcdefghijX`) | В UI срабатывает лимит: ввод 33-го символа блокируется атрибутом `maxlength="32"`, либо выводится ошибка *"Максимальная длина 32 символа"*. |
| 3 | Отправить API запрос с паролем длиной 33 символа | Ответ `400 Bad Request`, код `PASSWORD_TOO_LONG`. |

### [TC-SEC-004] Защита от брутфорса: блокировка после 5 неверных попыток (Rate Limiting)
- **Приоритет**: High
- **Тип**: Security / Negative
- **Слой**: API
- **Трассировка**: `SEC-103`
- **Предусловия**: Известен активный тестовый пользователь.

| № | Действие (Step) | Ожидаемый результат (Expected Result) |
|---|---|---|
| 1-4 | Отправить последовательно 4 запроса на смену пароля с неверным `oldPassword` | Каждый запрос возвращает `400 Bad Request` (`INVALID_CURRENT_PASSWORD`). |
| 5 | Отправить 5-й запрос с неверным `oldPassword` | Возвращается `400 Bad Request`. Лимит исчерпан. |
| 6 | Отправить 6-й запрос (даже с валидным `oldPassword`) | Возвращается статус `429 Too Many Requests`. Присутствует заголовок `Retry-After: 900`. Запрос на проверку в БД не выполняется. |

### [TC-SEC-005] Проверка принудительного разлогина сторонних устройств (Session Invalidation)
- **Приоритет**: Critical
- **Тип**: Integration / Security
- **Слой**: API / Session
- **Трассировка**: `SEC-102`
- **Предусловия**: 
  1. Пользователь авторизован в Браузере А (Сессия 1, DeviceId: A).
  2. Пользователь авторизован в Мобильном клиенте Б (Сессия 2, DeviceId: B).

| № | Действие (Step) | Ожидаемый результат (Expected Result) |
|---|---|---|
| 1 | В Браузере А успешно сменить пароль на новый | Запрос выполнен успешно (HTTP 200). В Redis обновлены токены для DeviceId: A. |
| 2 | В Мобильном клиенте Б выполнить любое действие (например: `GET /api/v1/profile`) | Запрос отклоняется со статусом `401 Unauthorized` (токен отозван). Клиент Б принудительно перенаправляется на экран логина. |
| 3 | Попробовать авторизоваться в Мобильном клиенте Б со старым паролем | Ошибка `401 Unauthorized`. |
| 4 | Авторизоваться в Мобильном клиенте Б с новым паролем | Успешный вход в систему, создана новая сессия. |
